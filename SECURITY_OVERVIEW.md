# Competition security overview

This is a shared-code league tracker hosted on free GitHub Pages with an existing Supabase database. Anyone may create a league; everyone who knows its one shared code has the same full management access. There are no conventional accounts or separate administrators. Devices remain authorized until explicit Leave or code rotation. Clearing browser data requires rejoining.

## Implemented controls

| Risk | Control | Evidence |
| --- | --- | --- |
| Unauthorized or cross-league access | Private-schema tables have RLS and no API-role grants. Each protected RPC verifies a server-stored league-specific grant. Directory returns only ID, name and creation time. Legacy anonymous RPC/table/view paths remain closed. | Real staging forged-token, ID substitution, private-table and old-RPC denial checks. |
| Shared-code guessing or disclosure | Existing pgcrypto bcrypt with random salts and cost 12; codes limited to 8–64 bytes with a letter and number/symbol. Raw codes never enter directory, backups, persistent draft storage, URLs or audit entries. Existing codes/grants are unchanged. | Direct weak-code/input tests; private credential access denied; wizard storage checks. |
| Automated abuse | Database-enforced creation cap: three per source per hour, plus 60 globally. Join cap: 60 per source and 30 per source/league per 15 minutes. No whole-league join lockout. Transient throttle windows pruned after two inactive days on later throttle calls. | Real bounded staging HTTP tests and forwarded-header request rejection. Distributed sources can still evade per-source limits; creation's global cap intentionally protects free infrastructure. |
| Stolen or revoked device credentials | Cryptographically random 256-bit browser tokens; only SHA-256 verifiers stored server-side. Leave removes that device's grant and private local caches; code rotation removes every grant and recorder lease. Every read/write/recovery checks the current grant. | Real Leave/rotation/recovery tests; browser persistence and cache-clear checks. |
| Duplicate or partial creation | PostgreSQL transaction, advisory lock, operation ID and request fingerprint; retries return the original league. Recovery requires the original random device grant and performs no creation. | Concurrent direct retries and browser lost-success-response/refresh checks. |
| Invalid data or stored script | Strict settings/team/player type, range, length, uniqueness and field validation. Text-tree guards reject markup/control characters and prototype keys. Names on setup/directory use textContent; team lists escape text. Imports have client guards, a 12 MiB size cap and existing integrity/league checks, followed by protected server validation. | Direct malformed requests plus browser markup/credential/foreign-league import checks. |
| Browser resource injection | CSP permits scripts only from the same origin, with no unsafe-inline/unsafe-eval. Reviewed event handlers moved to external code. Connections restricted to this Supabase project; object sources, base URI and form navigation denied. Inline styles remain permitted for existing layout. Referrer policy is no-referrer. | Browser must report no CSP violations; production HTTPS/source verification. |
| Concurrent scoring/data loss | Existing version/epoch/lease checks, one live recorder, acknowledged writes, local scoped recovery and immutable game-rule snapshots retained. | Full staging scoring, handoff, lost-acknowledgment, offline, simultaneous Start and custom overtime regression suite. |
| Untraceable management changes | Protected database triggers record league creation/rename, settings/team changes, reset, rotation and grant deletion. Audit has no client read/write grants, raw codes or tokens. At most 200 events per league; older than 30 days are removed when that league next has a management event. | Staging audit event counts and private audit API denial. Device reference is optional/pseudonymous and may be absent where PostgREST does not expose request context. It is not individual accountability. |
| Dependencies/secrets/error disclosure | Browser app has no runtime package/CDN dependencies. Browser test dependency pinned with lockfile. Client hides SQL-internal errors. Public anon keys are intentional and do not grant private data access. | npm audit: zero findings. Source/history role/private-key scan and denied API checks. |

## Hosting and access limitations

GitHub Pages serves static files and cannot provide a same-origin backend or set application-specific response headers. It cannot mint HttpOnly cookies. Cross-origin Supabase cookies would require third-party browser cookie support and would not provide a dependable seamless return flow. The existing JavaScript-readable device-token storage is retained: same-origin XSS, malicious browser extensions or another compromised page on this GitHub Pages origin can steal it. The strict script CSP, input/ import guards, server verification and revocation reduce risk; they do not make those tokens HttpOnly.

GitHub Pages cannot configure application-specific frame-ancestors/X-Frame-Options, Permissions-Policy or private cache headers. Meta CSP does not provide frame-ancestors protection. Live host headers were checked: HTTPS with HSTS max-age 31556952 and an HTML content type; no application-specific frame, permissions, content-type-options or CSP response headers. Public shell files have Cache-Control:max-age=600; no private league data is embedded in those files. A custom host or backend would be needed for the missing header capabilities; none was purchased or enabled. Private operations use non-cacheable POST requests and the client fetches them with cache:no-store. This is not cookie authentication; CSRF via automatically attached session cookies is not part of this access model. CORS is not relied on for authorization.

Rate limits protect bounded requests, not distributed denial of service. Bcrypt cost 12 is retained for compatibility with this existing pgcrypto architecture; OWASP prefers Argon2id for new systems when available. Everyone with the shared code can intentionally reset/edit data. Confirmation and backups protect against mistakes, not a malicious authorized participant.

No claim is made of MFA, independent penetration testing, end-to-end encryption, formal OWASP certification/compliance or complete security. Conventional Supabase Auth password warnings concern an unused account-login path. Advisers flag deliberately exposed SECURITY DEFINER RPCs and deny-by-default private tables; each app RPC's access predicate/grant is reviewed instead of weakening isolation to suppress those notices. Unused legacy functions remain denied to public API roles.

## Research and design sources

- [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): deny by default, enforce every request, and test tenant substitution.
- [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html): salted adaptive hashing and bcrypt work/input limits.
- [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html): unpredictable sessions, revocation and explicit browser-storage tradeoffs.
- [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html): transport, input bounds, safe errors and access validation.
- [Supabase securing the API](https://supabase.com/docs/guides/api/securing-your-api) and current MCP documentation search: private schema, explicit grants/RLS and privileged function boundaries.
- [Supabase changelog](https://supabase.com/changelog): reviewed October 10, including the September 25 PostgreSQL/pgcrypto update. This app uses bcrypt, not the legacy ciphers or ltree/btree_gist indexes described there; no paid upgrade or unrelated database extension operation was performed.
- [TeamSnap Add a sports organization team](https://helpme.teamsnap.com/article/1739-add-a-sports-organization-team): teams added from inside the organization/program.
- [LeagueApps Getting Started With Program Creation](https://support.leagueapps.com/hc/en-us/articles/360039382354-Getting-Started-With-Program-Creation): staged program/details setup, defaults and minimal optional fields. The app's exact two-step flow, grouped numbers, summary and empty state are original implementation choices.

## Validation and recovery

See `tests/SETUP_SECURITY_RESULTS.md`, `tests/BROWSER_RESULTS.md` and the final `IMPLEMENTATION_PROGRESS.md` entry for actual run IDs and rollout status. Synthetic data only is used in active security/browser tests. A private pre-migration schema snapshot is held outside this public repository. Production credential/session export was rejected by automatic approval review; those records stay in place and are checked with in-database fingerprints. This migration replaces functions/adds audit infrastructure without rewriting existing league or credential data. No service-role secrets, code hashes, reusable device tokens or user backups are checked into GitHub.

Recover by fixing forward on an isolated backend and deploying the reviewed frontend. An additive backend can remain in place while reverting this frontend to the preceding tested multi-league release. Preserve newly written data and empty leagues; do not blindly restore an old data snapshot, restore an old anonymous API, or reopen legacy grants. The previous UI requires at least two teams for normal edits, so repair the updated UI if empty leagues already exist. Audits record future events only; historical actions cannot be reconstructed.
